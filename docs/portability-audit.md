# Portability audit for the muxless VR bridge

This audit records the original V3 package and the implementation plan for 0.3. The source links lead to the corresponding files in the published implementation.

## Target and scope

Use one uncompressed display path for AMD and NVIDIA render GPUs paired with Intel and AMD display GPUs. The headset and its driver supply display and tracking information through the VR runtime or OS. SteamVR is the first runtime integration. Monado should be able to use the same transfer and scanout implementation through its compositor target interface.

The original V3 package did not meet that target. Its required synchronization handles depend on driver implementation details, its display capabilities reflect the original WMR setup, and its installation and activation are tied to SteamVR. AMD-to-AMD on WMR is the V3 configuration exercised locally. The NVIDIA-to-Intel Rift S report demonstrates display output from the released implementation, which used a different synchronization contract. [V3 README](../README.md) · [Issue #1 report](https://github.com/vibudh007/Muxless-VR-Bridge/issues/1#issuecomment-6904116394)

The dGPU and iGPU roles define the topology. The machine also has to provide a Vulkan driver capable of exporting compatible memory and synchronization, a working VR runtime and headset driver, and permission to drive the headset connector through DRM. Under Wayland, the compositor must offer the connector for leasing and grant the lease. Two GPUs can be present even when those capabilities are missing. Those limits should appear as precise startup errors. The bridge should work with conforming drivers irrespective of vendor. Mesa is one implementation of those APIs. [Vulkan external resources](https://docs.vulkan.org/guide/latest/extensions/external.html) · [Wayland DRM lease protocol](https://github.com/wayland-mirror/wayland-protocols/blob/main/staging/drm-lease/drm-lease-v1.xml) · [DRM userspace API](https://docs.kernel.org/gpu/drm-uapi.html#display-resource-leasing)

## What needs to change

| Area | Current behavior | Required change |
| --- | --- | --- |
| Frame synchronization | Vulkan exports `OPAQUE_FD` timelines for every slot. The iGPU opens them as DRM sync objects and converts the ready point back to a Linux sync file before each commit. Vulkan export capability alone cannot establish that these descriptors are DRM objects. NVIDIA has documented the incompatibility. | Export a binary Vulkan semaphore as `SYNC_FD` after submitting the copy. Give the resulting Linux sync file directly to the leased KMS plane through `IN_FENCE_FD`. Release the previously displayed slot on its replacement's page-flip event. Use this contract for all four GPU pairings. [Vulkan startup check](../src/transport.cpp) · [KMS import and commit](../src/headset.cpp) · [NVIDIA explanation](https://github.com/KhronosGroup/Vulkan-Docs/issues/2473) |
| Display timing | Device creation requires external-fence FD support and an exportable `OPAQUE_FD` fence. The first-pixel hook tries to signal that fence through a DRM sync object. Actual CRTC counters are already available. | Remove the startup requirement for the opaque display-event fence. Keep real mode duration, sequence and monotonic presentation timestamps. Put timing delivery to SteamVR in its adapter and validate how it behaves when the proprietary first-pixel mechanism is unavailable. [Device preflight](../src/layer.cpp) · [Display event](../src/headset.cpp) · [Display counter](../src/headset.cpp) |
| DMA-BUF allocation | The shared image defaults to a linear modifier, while the desktop experiments can request AMD-specific tiled memory or BAR-visible device-local memory. Headset copy rejects any shared heap except uncached, host-visible, coherent system memory. Local render memory also rejects device-local memory that happens to be host visible. | Derive the format and modifier intersection from Vulkan and the leased KMS plane. Require a compatible exportable allocation and real PRIME import. Prefer a suitable shared-memory layout for scanout and device-local storage for the compositor image. Let Vulkan memory requirements and actual import decide correctness. The GPU-only copy does not require CPU mapping, so CPU cache/coherency flags are not eligibility rules. [Modifier and image setup](../src/transport.cpp) · [Image preflight](../src/transport.cpp) · [Heap selection](../src/transport.cpp) |
| Copy queue and GPU selection | The launcher applies Mesa `DRI_PRIME` or NVIDIA PRIME/Optimus/GLX environment settings, and enables a RADV experimental option. The layer selects the transfer queue by RADV driver ID and checks that the actual Vulkan render device is discrete. The launcher can otherwise pick the first enumerated PCI candidate in sorted order. | Separate runtime GPU selection from the bridge. Key the render side to the actual Vulkan device and the display side to the device that owns the connector in the lease. Verify the selected device against the runtime's selection where available. Use Vulkan queue capabilities and existing runtime queues, so a private transfer queue and vendor flags are unnecessary for core operation. [GPU picker](../shim/gpu_launch.hpp) · [Launcher](../shim/launcher.cpp) · [Queue selection](../src/layer.cpp) |
| Headset mode and surface | The first choice is 2880×1440 at 90 Hz. Another headset can get one alternate mode if DRM marks it preferred and its dimensions differ. Virtual surface support reports success for every queried GPU and queue family. The layer exposes fixed surface formats, identity transform and opaque FIFO behavior, and the KMS code selects a primary plane before testing the framebuffer. | Take modes and connector identity from DRM/runtime data. Honor a valid runtime-requested mode, then its advertised native mode or an unambiguous choice. Publish only the devices, queues, modes, formats, usage, transforms and image counts that can actually present. Validate the actual request before scanout, including its transform. [Mode choice](../src/headset.cpp) · [Virtual limits](../src/virtual-display.cpp) · [Surface support](../src/virtual-display.cpp) · [Plane selection](../src/headset.cpp) |
| Lease ownership and lifecycle | Lease and display discovery use process-global state and synthetic tokens. The layer validates the leased device and connector, duplicates the FD and runs a real `TEST_ONLY` commit at framebuffer creation. | Keep those checks. Scope authorization, connector/CRTC/plane identity and frame state to an output session and lease generation. Recompute them on hotplug, lease revocation, mode change or runtime restart. Handle a lease that grants fewer resources than requested and a connector that disappears during startup. [Global state](../src/virtual-display.cpp) · [Lease validation](../src/virtual-display.cpp) · [Framebuffer test](../src/headset.cpp) |
| Runtime and package | The Vulkan layer recognizes SteamVR executable names. The manager looks up Steam, modifies SteamVR launch options and checks whether its DSO is mapped into `vrcompositor`. Oasis detection is informational. The package also installs a SteamVR repair layer and can require administrator approval for an AMD sysfs profile helper. | Keep the SteamVR adapter and installer integration specific to SteamVR. Make patch activation independent of bridge readiness. Remove the automatic profile helper and its authorization from the default install and runtime; keep any desired hardware tuning in a separate user-controlled tool. Retain the existing public package names. ## One frame path

1. **Negotiate the output at startup.** The runtime adapter supplies the render device and the display request or the already acquired lease. Identify the display GPU from the DRM FD and use the actual leased connector, CRTC and compatible plane. Match the runtime's native extent and refresh with the display modes. Use the KMS plane's format/modifier capabilities and Vulkan external-image queries with the actual image usage, sharing mode and extent. Allocate a persistent ring on the producer and verify the resulting DMA-BUF plane layout, PRIME import, framebuffer, and atomic `TEST_ONLY` on the consumer. Trying eligible formats and memory types during negotiation still results in one allocation and presentation protocol. [Vulkan DMA-BUF](https://docs.vulkan.org/refpages/latest/refpages/source/VK_EXT_external_memory_dma_buf.html) · [Vulkan image modifiers](https://docs.vulkan.org/refpages/latest/refpages/source/VK_EXT_image_drm_format_modifier.html) · [KMS plane and framebuffer properties](https://docs.kernel.org/gpu/drm-kms.html)
2. **Copy and queue the frame.** The runtime completes rendering, distortion and composition on the dGPU. The bridge submits a GPU copy from that final image to the shared slot, waiting on the runtime's completion dependency. Perform the Vulkan layout/access transitions and external queue-family ownership release required by the chosen image contract. Signal a binary exportable semaphore in the same submission, export its sync file while the signal can still be pending, and submit it to atomic KMS as the plane input fence. Reuse recorded commands and the buffer ring. The CPU manages submission and FD lifetimes. Pixel data stays off the CPU. [Vulkan semaphore FD export](https://docs.vulkan.org/refpages/latest/refpages/source/vkGetSemaphoreFdKHR.html) · [Foreign queue-family ownership](https://docs.vulkan.org/refpages/latest/refpages/source/VK_EXT_queue_family_foreign.html) · [KMS explicit fencing](https://docs.kernel.org/gpu/drm-kms.html#explicit-fencing-properties)
3. **Retire render and display resources separately.** Track copy submission completion for source-image and command reuse. Keep the shared slot pinned while it is pending and while it is scanned out. A completed activation of the next framebuffer releases the previous slot. A slot that just became visible is still in use. Before handing it back to Vulkan, establish that KMS has stopped reading it and return external queue ownership as required. Attribute sequence/timestamp feedback to the exact submitted frame and lease generation. Handle a failed atomic commit, queue/device loss or a revoked lease without signalling false completion or reusing a slot the kernel may still own. Vulkan-internal retirement can use Vulkan primitives that never cross into DRM. [Current replacement event handling](../src/headset.cpp) · [Linux sync-file API](https://docs.kernel.org/driver-api/sync_file.html)

The display-side API owns the mode, buffer registration, presentation and release. The SteamVR adapter translates Vulkan display/WSI operations and its timing requests into that API. A future Monado adapter should integrate at `comp_target`, where Monado already owns the final composited image, the GPU-ready dependency, and frame pacing. Give the core a device, final image, completion dependency, output description and frame ID. Report presentation and release back to the adapter. Both adapters use the same core. The Oculus Rift S driver using Monado under SteamVR still exercises the SteamVR adapter. Adding a process name to the existing Vulkan gate would leave native Monado's target and pacing integration unimplemented. [Current Vulkan display hooks](../src/virtual-display.cpp) · [Monado compositor target](https://monado.pages.freedesktop.org/monado/structcomp__target.html) · [OpenXR Vulkan device selection](https://registry.khronos.org/OpenXR/specs/1.1/man/html/xrGetVulkanGraphicsDevice2KHR.html)

The SteamVR adapter also has two correctness requirements. For a valid `oldSwapchain`, return the old chain to the retired state even if creating the replacement fails. Current color space, extension-chain and lease failures can return before that happens. Keep any acquired or kernel-owned images alive for their remaining lifetime. For first-pixel timing, directly swapping Vulkan fence handle types cannot turn a KMS vblank into a signal for a Vulkan fence. Use the runtime's supported counter/timing interface or explicitly implement and measure genuine KMS-event-to-Vulkan signaling in the adapter if SteamVR requires the fence. Real page-flip detection and buffer release must work independently of that adapter feature. [Early swapchain exits](../src/layer.cpp) · [Vulkan retirement rule](https://docs.vulkan.org/refpages/latest/refpages/source/VkSwapchainCreateInfoKHR.html) · [Vulkan display-control extension](https://docs.vulkan.org/refpages/latest/refpages/source/VK_EXT_display_control.html)

## Dependency boundary

- **Display core:** Linux DRM/KMS, libdrm, Vulkan and its installed driver, Linux DMA-BUF and sync files. A Wayland integration needs the DRM lease protocol wherever the runtime obtains its display lease through Wayland. The core can use a previously granted lease FD without opening a second Wayland lease for the same connector.
- **SteamVR integration:** Vulkan layer registration and SteamVR’s display/WSI contract. Any Steam GPU environment setup must stay inside this integration while SteamVR relies on it. To meet the target, verify the actual compositor render device and establish a supported route that needs no vendor-specific launcher setting. A bridge can validate the Vulkan device it receives. Forcing a separate Steam, game or Proton process onto that device requires cooperation from the runtime or the process's graphics stack. [Valve’s Vulkan device-selection sample](https://github.com/ValveSoftware/openvr/blob/master/samples/hellovr_vulkan/hellovr_vulkan_main.cpp)
- **Tests and packaging:** Keep laptop-window, XRandR/synthetic display and fixed 90 Hz test code outside the headset path. The desktop fixture currently requires additional Wayland protocols including timeline sync objects. Those are test dependencies. AppImage, build containers, C++ toolchain, and the current x86-64/glibc packaging baseline belong to delivery or development. [Desktop protocol requirements](../src/desktop.cpp) · [Build script](../shim/build.sh) · [AppImage assembly](../shim/appimage/assemble.py)

Headset drivers remain responsible for tracking, lens calibration, stereo layout, and any headset-specific activation. The bridge presents the runtime's completed image. The runtime must match panel orientation, advertised native timing, and any multi-output layout with the image it submits. Extend the output contract to represent a set of leased outputs if a runtime needs it. A single connector at a given mode cannot represent every headset topology.

## Implementation and verification order

1. Replace the shared opaque timelines with the binary sync-file handoff in the one headset path. Keep exact scanout release ordering and document the SteamVR timing contract before removing the first-pixel implementation. Exercise real counters and pacing on WMR at native 2880×1440 and 90 Hz. A `SYNC_FD` export is a per-frame operation. Measure submit-to-ready and ready-to-flip tails and missed/repeated vblanks against V3. An uncompressed 32-bit 2880×1440 image is 16.59 MB, or 1.49 GB/s at 90 Hz for one copy, before pitch padding and display reads. Performance depends on the link and memory system. The common API alone makes no latency guarantee.
2. Make mode, transform, format/modifier and memory selection capability-driven. Move fixed fixture settings out of the headset path. Test native WMR and replay a mode inventory with the issue #1 Rift S portrait mode at 1440×2560 and 80 Hz, including absence of the preferred flag, plus lease loss and swapchain recreation. Keep uncompressed native output. [Rift S system report](https://github.com/user-attachments/files/34892846/SteamVR-2026-11-15-PM_08_22_46.txt)
3. Separate the renderer/device selection and SteamVR adapter from the core. Verify the bridge presents with the repair layer disabled and without requiring the AMD profile helper. Verify SteamVR startup behavior separately from first flip, game frame timing and desktop UI. Document the adapter contract so Monado can supply a live Vulkan completion point and receive timing/release without Steam-specific hooks.
4. Add startup-only evidence. Record the actual Vulkan device and driver, leased DRM node and connector, mode, plane, format/modifier and allocation, sync-file export and KMS acceptance, `TEST_ONLY`, and first real page flip. The current `TEST_ONLY` uses `IN_FENCE_FD=-1`, so it checks the mode and framebuffer independently of that handoff. `--doctor` currently queries generic `SYNC_FD` and DMA-BUF capabilities and counts Wayland lease globals. `--verify --runtime` checks DSO mapping. Report these as distinct from a working lease and completed scanout. Log errors with the failed operation and Vulkan result or DRM errno. Keep frame tracing opt-in. [Framebuffer test](../src/headset.cpp) · [Current probe](../shim/appimage/probe.cpp) · [Current runtime check](../shim/appimage/manager.cpp)
